<objective>
Build the import engine for DATA-04 as a prepare / commit pipeline over a typed in-memory
snapshot: parse and validate JSON or CSV files, produce a preview (counts, date range,
warnings), then commit through a safety backup and one atomic Isar transaction.

Purpose: D-11 requires atomic replace with an automatic safety backup and a confirmation
screen; D-14 limits CSV to the entities supplied; research found that every existing
DAO opens its own write transaction, so the importer must use the collections directly
inside one `writeTxn`. The Isar auto-increment behaviour after explicit-id writes
(assumption A4) is proven first because everything else depends on it.

Output: engine, domain contracts and tests. The pick/confirm screens and the post-import
alert and reconcile hooks are plan 04-17.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User-selected file -> parser | The file is fully untrusted: arbitrary bytes, size, structure and content. |
| Parser -> write transaction | Only a fully validated snapshot may cross; nothing partial. |
| File name -> file system | Picked names must never influence where anything is written. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-04-11-01 | Tampering | Malformed or hostile JSON/CSV (wrong types, unknown enums, huge strings, duplicate ids, duplicate unique keys) | high | mitigate | Strict readers (04-04, 04-08), per-collection row cap, duplicate-id and budget-key checks in validateSnapshot, all before any write; unit tests per rule. |
| T-04-11-02 | Denial of service | Oversized file | high | mitigate | Size cap (25 MiB) checked on the byte length BEFORE decoding; row cap 200000 per collection. |
| T-04-11-03 | Tampering | Partial application leaving a mixed database | high | mitigate | One writeTxn: clear and putAll together, abort and rethrow on any error; asserted by a rollback test that forces a unique-key failure after the clears. |
| T-04-11-04 | Information disclosure | Safety backups accumulate private data | medium | mitigate | Written only to the app-private documents directory, newest three kept, older deleted, no share intent (D-12); excluded from Android Auto Backup by plan 04-05 (D-13). |
| T-04-11-05 | Tampering | Path traversal through a crafted file name | medium | mitigate | Safety file names are generated from the clock; picked file names are used only to label errors, never for paths (CWE-22). |
| T-04-11-06 | Repudiation | Silent data loss on a failed import | medium | mitigate | commit refuses to start the transaction if the safety backup cannot be written; the safety path is retained and surfaced by the UI (04-17). |
</threat_model>
