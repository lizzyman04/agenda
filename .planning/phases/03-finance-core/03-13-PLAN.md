<objective>
Build the one piece of test infrastructure this project has never had: a way to open a
**real** `isar_community` instance inside `flutter test`, against an isolated temp
directory, and tear it down cleanly.

Why this cannot be skipped: `.limit(500)`-without-`sortBy` has now been the root cause of
three Critical findings in this phase (CR-04, and the two `BL-01` gaps this fixes next in
03-14). Every regression test written against this defect class so far
(`transaction_dao_ordering_test.dart`) asserts on DAO **source text**
(`File(path).readAsStringSync()` + substring match), not on query **behavior** — filed as
WR-D6 in `03-REVIEW.md`, which states plainly: these tests "pass unchanged whether the bug
is present or not." A mocked repository cannot substitute either, because `.limit(500)`
lives in the DAO, below the repository layer that gets mocked. The only fix is a real Isar
instance in the test process.

**The user has locked this decision: build the real-Isar harness.** This is not being
re-evaluated here.

**A second decision this plan must also settle, surfaced by plan-checker revision, and
already corrected once by that same revision process — read this carefully before writing
Task 1, it records a mistake this plan already made once:**
`isar_community` 3.3.2's own core-download path (`lib/src/native/isar_core.dart`,
`_downloadIsarCore`) is a bare check-then-act with no lock file and no atomic
temp-then-rename — it checks whether the destination file exists, and if not, streams the
download straight to that final path. Two OS processes racing that write can corrupt or
partially write the native library both then try to load via `DynamicLibrary.open()`. This
is not theoretical: `flutter test` runs test files as **separate concurrent OS processes**
by default (`-j`/`--concurrency`), this project's CI (`.github/workflows/ci.yml`) runs
`flutter test --no-pub --coverage` unqualified on a fresh `ubuntu-latest` runner with zero
cached binary every push, and after 03-14 lands there will be two files that call into this
harness — enough for the race to trigger on essentially every CI run. The harness's own
per-process `_coreInitialized` guard cannot fix this, because that guard is per-process and
the race is cross-process.

**This plan's first attempt at a mitigation was a `dart run tool/warm_isar_core.dart` CI
step, and it was a no-op.** `_downloadIsarCore`'s destination directory is derived from
`Platform.script`'s parent directory, and `Platform.script` resolves differently depending
on how the process was launched: a `dart run tool/warm_isar_core.dart` invocation resolves
`Platform.script` to `<repo>/tool/warm_isar_core.dart`, so the binary is cached under
`<repo>/tool/`; a `flutter test` worker resolves `Platform.script` to a synthetic
`<repo>/main.dart` entrypoint, so it caches (and looks for) the binary under `<repo>/`
directly. Different directories — the pre-warm step wrote to a location the later parallel
`flutter test` workers never check, so the race it was meant to prevent still occurred on
every cold-cache run. **The corrected mitigation makes the pre-warm step itself a
`flutter test` invocation** (`test/support/_warm_isar_core_test.dart`, run with `-j 1`),
so it resolves `Platform.script` — and therefore the download path — identically to the
later parallel workers, structurally, with no independently-derived path for anyone to
keep in sync by hand. This is detailed in Task 1.

Purpose: give 03-14 (and any future DAO test) a genuine behavioral foundation instead of
another source-text assertion — and make sure that foundation is actually reliable in CI,
not just something that looks reliable while writing to a path nothing else reads.
Output: `test/support/isar_test_harness.dart` (the reusable helper),
`test/support/isar_test_harness_test.dart` (proof it works),
`test/support/_warm_isar_core_test.dart` (the CI pre-warm trigger, itself a `flutter test`
file), and a `.github/workflows/ci.yml` step that runs it before the main `Test` step.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process -> local filesystem (OS temp dir) | The harness opens a real Isar database file under the OS temp directory for the lifetime of a test run. |
| dev/CI machine -> network (Isar Core binary) | `Isar.initializeIsarCore(download: true)` fetches a native binary over HTTPS the first time a machine with no cached binary runs a test that opens the harness. |
| CI job -> parallel `flutter test` worker processes | Multiple test files sharing one `flutter test` invocation run as separate OS processes that can race on the same on-disk binary-download destination. |
