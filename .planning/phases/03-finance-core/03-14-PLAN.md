<objective>
Close the two `BL-01` gaps from `03-VERIFICATION.md` (roadmap success criteria 2 and 3):
`TransactionDao.findByMonth` and `TransactionDao.findByLinkedGoal` still carry
`.limit(500)` with **no `sortBy`**, exactly as `03-REVIEW.md`'s BL-01 finding and this
phase's own verification confirmed by direct source read. Both feed money **totals**, not
display lists — `BudgetCubit._reload` folds `findByMonth`'s result into per-category
spend and the over-limit warning; `GoalCubit._refreshGoal` folds `findByLinkedGoal`'s
result into `taggedCents`, half of `SavingsGoal.progressPercent`. Isar returns unsorted
rows in id (insertion) order, so the cap silently keeps the OLDEST 500 and drops the
user's most recent activity — the identical failure mode CR-04 already fixed once for
`findAll`/`findAllForAggregates` in plan 03-09, left half-done for these two methods.

Root cause and fix direction are already settled by the review — do not re-diagnose.
These are aggregate reads, not pages: uncap them, mirroring `findAllForAggregates`
exactly. No repository or cubit signature changes are needed — `getByMonth`/
`getByLinkedGoal` already exist end-to-end and already call `findByMonth`/
`findByLinkedGoal`; only the DAO method bodies and the file's class doc change.

Also in scope: the class doc at the top of `transaction_dao.dart` currently claims
`findAllForAggregates` is "the single, deliberate exception" to the 500-row cap. That
is false today (`findByLinkedGoal` is already uncapped-adjacent... no — currently it is
still capped, so the doc is doubly wrong: two more uncapped methods will exist after this
plan, and the doc must name all of them, not just one). Correcting it is exactly what let
03-09 stop early last time — a future reader trusting the old doc would conclude the
aggregate problem was already fully solved.

This plan writes the regression test FIRST, using the real-Isar harness from 03-13,
confirming it fails against the still-capped code — then fixes the DAO. Per WR-D6 in
`03-REVIEW.md`, a source-text assertion for these two methods would prove nothing; the
harness makes a genuinely behavioral test possible for the first time in this project.

Purpose: a budget bar or goal-progress figure that silently under-reports is worse than
one that shows nothing — it tells the user they are safely under a limit they may have
already blown, or further from a goal than they actually are.
</objective>
