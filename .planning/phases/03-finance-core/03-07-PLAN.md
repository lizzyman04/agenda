<objective>
Close UAT test 3 (severity: major). Swiping a second transaction away while the
first delete's undo SnackBar is still visible does not replace that SnackBar —
Material queues it FIFO. The user sees one SnackBar, believes it belongs to the
swipe they just made, taps Desfazer, and the FIRST transaction comes back while
the one they actually just deleted stays deleted.

Root cause (already diagnosed in 03-UAT.md, do not re-diagnose):
`_handleDelete` in `transaction_list_screen.dart` calls
`ScaffoldMessenger.of(context).showSnackBar(...)` with no
`hideCurrentSnackBar()` first. The undo itself is correctly id-based
(`cubit.restoreTransaction(tx.id)`) — this is purely a SnackBar-lifecycle
defect, not a wrong-id lookup.

Explicitly NOT in scope: the undo-timer / auto-dismiss defect. That was a
different bug (Flutter 3.38 made `SnackBar.persist` default to `action != null`),
already fixed in commit `d102f2b` via `persist: false` at the three undo call
sites, with regression tests in
`test/presentation/undo_snackbar_auto_dismiss_test.dart`. Leave `persist: false`,
`duration: AppConstants.undoSnackbarDuration` and that test file alone.

Purpose: a delete the user cannot reliably undo is a data-loss bug on FIN-03.
Output: one-line lifecycle fix plus a widget test that fails against the current
code for two independent reasons.
</objective>
