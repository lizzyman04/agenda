# Phase 3.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

**Phase character:** pure refactor. No new runtime behavior is introduced, so
validation is dominated by *regression detection* rather than new-feature proof.
The suite that must stay green is the one that exists today: 230 tests.

## Sampling Rate

- **After every task commit:** `flutter analyze` on the touched path + `flutter test test/<touched_dir>/`
- **After every plan wave:** `flutter test --no-pub` (full suite) + `dart run tool/check_architecture.dart`
- **Before `/gsd-verify-work`:** full suite green, guard exits 0, analyzer clean
- **Max feedback latency:** ~35 seconds

**Refactor-specific rule:** the test count must not *drop*. A split that
accidentally orphans a test file still leaves a green suite, so each wave
compares the reported test count against the 230 baseline (plus any tests the
phase deliberately adds). A decrease is a failure even when everything is green.

## Wave 0 Requirements

- [ ] `tool/check_architecture.dart` — the line-count, directory-size, and
      README-presence guard. **Build this first, in Wave 0, not last.** The
      roadmap places it in plan 3.1-05, but writing it early in
      *informational* mode (prints violations, exits 0) turns every subsequent
      plan into a measurable step instead of a guess. Flip it to failing mode
      (`--fatal`, wired into CI) only once the tree is compliant.
- [ ] `tool/architecture_exemptions.dart` (or a plain allowlist file) — required
      before the guard can be enforced, since at least one file is expected to
      be deliberately exempted rather than split. Each entry must carry a
      one-line justification; an exemption without a reason is a rule with a
      hole in it.

*No new test fixtures or directories are needed — this phase adds no runtime
behavior, only a dev-time script.*

## Manual-Only Verifications

| Behavior | Why Manual | Test Instructions |
|----------|------------|-------------------|
| Split screens with no widget-test coverage still render and accept input | Several of the twelve screens in scope for 3.1-01/3.1-02 have **zero dedicated widget tests** — `flutter test` passing cannot catch a regression in them, making SC-4 a weak signal for exactly the files this phase changes most | After each screen split: install on device via adb, open the screen, enter data in every field group, save, reopen and confirm the values persisted |
| Controller lifetime across a split | The classic failure of this refactor is passing a `TextEditingController` into an extracted widget that then disposes it — the crash is a runtime-only symptom | Watch for `TextEditingController used after being disposed`; the screen owns controllers, extracted widgets receive values + callbacks (see `lib/presentation/finance/goals/README.md`) |
| Isar models still load after a directory move | Moving a model relocates its `part 'x.g.dart'` pairing and stales `injection.config.dart`; the analyzer may pass while persistence breaks | After 3.1-04: `dart run build_runner build --delete-conflicting-outputs`, then cold-start the app and confirm existing transactions, budgets, goals, and debts still read back |

**This is the phase's real risk.** A refactor that keeps the suite green while
silently breaking an untested screen is the expected failure mode, not an
unlikely one. The manual passes above are not optional polish.
